Chapter 1 What Pulse Weaver is

Pulse Weaver Studio is an independent Windows streaming and recording application derived from OBS Studio. It combines OBS capture, composition, audio and output technology with a show-oriented interface: Show Control, Camera, saved Stages and Looks, landscape and portrait production, platform connections and companion integrations.

The aim is to help one operator build and run a coherent show. A streamer can prepare several presentations, route the right compositions to the right destinations, watch chat and change the show with deliberate cues. A hobbyist can use only a small subset; a complex production can use paired canvases, saved motion, alerts and external controllers.

Version 2.0.1 is the latest regular Windows release identified by the current local README. Separate preview, alpha, unstable, Lite and Apple Silicon lines have their own identities and feature boundaries. A version number in a historic entry describes that record at that time, not necessarily the state of every edition today.

The show at a glance

Inputs → scene items → scenes and canvases → Stage and Look → routing → encoder → stream or recording

The arrows are a useful conceptual model, not a literal description of every internal call. A Stage coordinates scene assignments and routes; a Look supplies a saved target for scene-item presentation. Destination-specific exclusions and rendering copies can affect what a particular output receives.

Chapter 2 Pulse Weaver and OBS

OBS Studio is free open-source production software. It captures video and audio, arranges sources into scenes, mixes audio, applies filters, encodes and records or streams the result. It supports docks, Studio Mode, hotkeys, transitions, scripting, plugins and built-in WebSocket control. See https://obsproject.com/ and https://obsproject.com/kb/sources-guide.

Pulse Weaver is a fork, not an independent video engine or merely a dashboard that requires another copy of OBS to run. Its native application uses libobs and OBS frontend APIs directly. The architecture file identifies the base as OBS Studio 32.2.2, though a later Pulse Weaver build may have further changes. It is independent of the OBS project and distributed under GPL version 2 or later.

The common ground includes scenes, source types, transforms, filters, mixing, browser sources, encoders, recording and streaming. OBS users can accomplish many additional workflows with plugins and external applications. Pulse Weaver’s distinguishing approach is to integrate its preferred show-control model, paired layouts, routing, chat and integrations into a single product experience.

Working vocabulary for an OBS user

OBS scene: the composition of sources. Pulse Weaver still uses this building block.

Pulse Weaver Stage: a higher-level show context that coordinates scene and output assignments.

Pulse Weaver visual Look: a saved arrangement or presentation within a Stage.

Pulse Weaver Show Control: the operating surface for Stages, output, chat and quick audio controls.

Pulse Weaver Camera: the native scene/source editor for available canvases, including the independent HUD in the 2.0 workflow.

OBS Studio Mode allows previewing a scene before transitioning it to programme. Pulse Weaver’s newer Show and Control split gives production preparation and live operation their own product surfaces, but an edit to a live shared scene or source can still be visible. Do not assume a private edit simply because an editor is open. https://obsproject.com/kb/obs-studio-overview

OBS has a mature cross-platform ecosystem on Windows, macOS and Linux. The documented regular Pulse Weaver 2.0.1 release is Windows x64. Plugin compatibility, upstream fixes, testing and edition availability must be assessed for the installed Pulse Weaver build, not inferred from OBS compatibility alone.

Chapter 3 The production model

Sources and scene items

A source produces or supplies content: a webcam, a game, a window, an image, browser page, media file or audio device. A scene item is a particular use of a source in a scene. The source may be shared, while each scene item has its own placement, size, crop, visibility and layer order.

For example, one presenter webcam source can appear as a small corner inset in a landscape gameplay scene and as a wide top band in a portrait scene. Changing the item’s position in one scene differs from changing the shared camera device settings. A source-level change can affect other places that use the same source.

Scenes and canvases

A scene gathers scene items into a composition. The canvas supplies the dimensions and space for composition. The landscape and portrait versions need their own deliberate framing; a layout suitable for a wide display is rarely appropriate when copied unchanged into a tall display. A source can be reused across both, but their scene items and transforms are separate.

Stages and Looks

A Stage represents a meaningful show context and holds or coordinates the scene and routing assignments associated with it. A Look is an operating presentation within that context, such as Game leads or Presenter reacts. The newer setup guide calls a Look a layout that can be switched within a Stage. A visual Look is distinct from a physical lighting Look.

Main Stage
  Landscape scene + Portrait scene
  Look: Gameplay        → game large, camera small
  Look: Presenter       → camera large, game supporting
  Look: Screen share    → screen primary, camera inset

This is a teaching example rather than a rigid schema. Existing shows may organize Stages differently. A Stage can also carry destination-specific assignments and source exclusions. A Look is not necessarily a new scene or a full copy of every input.

Chapter 4 Stages Looks and scenes in depth

What a Stage owns or coordinates

A Stage brings together the show context, paired scene choices, format-specific transition choices and output assignments. It can use different scenes or exclusions for particular destinations. The destination output plan remains a separate concern: assigning a scene to a route does not automatically enable a destination or start a stream.

A Stage can represent Main, Starting, Break, Ending or any other useful operating context. The latest default builder places chosen live layouts into one shared Main Stage and creates selected surrounding screens as separate Stages. This is a change from earlier four-page wizard models and is a good example of why version-specific instructions matter.

What a Look saves

A Look is a named saved presentation. It can include target position, scale, crop, visibility and order for controlled scene items, with independent landscape and portrait target arrangements. Reusing stable scene-item identities within a Stage lets the motion system move the same visual unit between Looks. A Look is not automatically a new camera source or a separate scene.

Create another Look when you need to choose a different focus or presentation while broadcasting. A camera frame shape, theme color, logo, or source assignment usually configures the selected Look. If you actually want to change emphasis live, that alternate focus is an operating Look. One size, border and color combination need not be multiplied into dozens of saved Looks.

What a scene does

The OBS engine renders the scene’s items in order. Sources higher in the stack can cover those below. A saved Look can change the presentation of items, but it cannot conjure up a missing source, make an incorrect scene assignment correct, or guarantee that a service is connected.

Worked example

A Main Stage has one landscape scene and one portrait scene. Both include a game and presenter. Game leads makes the game dominant and the camera small. Presenter reacts enlarges the camera and retains a smaller game. The same logical Look has independent H and V compositions: a side-by-side arrangement may work in H, while a vertical stack works in V. The same underlying webcam may feed both, but each canvas has its own item and geometry.

At the end of a match, run Presenter reacts. The source items move or change to their saved targets. When gameplay resumes, run Game leads. When leaving for a break, select the Break Stage. The Stage change uses its configured transition; the Look movement is a different mechanism.

Identity and shared objects

Names help people recognize items; source UUIDs and scene-item identities distinguish objects. A reused source can appear more than once, so matching by name alone can target the wrong item. Related Looks should reuse the intended item within each canvas when continuity is desired. Portrait items have their own identity. Replacing a layer requires checking its saved targets and any restore snapshots as well as the scene itself.

Chapter 5 Building a show

In the 2.0 guide, open Show → Control → Build my show. The default flow has two required pages. First choose only the layouts and screens you need. Second name the show, supply the necessary inputs, review and create it. The older detailed builder remains available for saved layouts and specialist arrangements.

Page one choose results

The guide lists Camera, Face + activity, Activity + face, Screen share, Screen + two cameras, Gameplay and Game + two cameras. Optional surrounding screens include Starting, Break, Ending and Celebration or announcement. An activity can be a workbench, instrument, demonstration, pet or other subject; it is not tied to one specific device.

Nothing needs to be generated merely because it is possible. Basic gameplay, screen or activity layouts may omit a face camera. A two-camera composition requires two different pictures. A show made only of holding screens needs no capture sources.

Page two assign and review

Assign existing inputs or draft new cameras, captures, images, video or browser sources. The same input can be reused across selected Looks. Review both canvas illustrations and verify real pictures after creation: an inactive or new capture may be represented by an estimated aspect ratio. Wide content is fitted rather than assumed to be safe to crop.

Optional editors cover camera framing and color, per-format Stage transitions, up to three alert layers per format, and screen messages or artwork. The built-in Starting screen is a static message; it is not a running timer. A provider’s actual browser artwork or widget can provide animation or a countdown.

Back preserves draft answers, cancelling an optional editor restores its previous answers, and cancelling the wizard creates no partial show. Stop outputs before creating the show and check actual framing and alert audio afterwards. Existing catalogue entries are preserved according to the guide; creation does not start a broadcast or verify third-party commands.

Chapter 6 Movement and transitions

A Stage transition and a Look movement answer different questions. A Stage transition changes between show contexts or assigned scenes, using Cut, Fade or an available stinger. A Look movement changes the position and presentation of items within a Stage. An OBS item show/hide fade is yet another mechanism and does not by itself reproduce a slide or a resize.

A stinger is a video transition with a configured switch point. Its own media timing determines its duration; it is not simply a fade duration. In 2.0.1 Manage Stages, transition type and timing are grouped per format; fade has an editable duration, Cut is instant, and stinger timing comes from the transition.

The 2.0 notes describe smoother camera reflow and a 1.05-second default movement for new Looks, preserving custom saved timings. That does not promise that every imported Move filter, animation path, group or third-party transition behaves identically. Check the installed feature and import report.

A movement rehearsal

Start at Gameplay Focus. Run Presenter Focus. Watch the opening frame, several intermediate frames, the endpoint and the return. Check the camera frame, crop, background coverage and alert stack. Repeat in both orientations. A correct endpoint can hide a bad path: an enlarging camera may expose empty background, cover chat or crop a face on the way.

Do not save a Look accidentally while looking at a mid-animation preview. Where supported, use the editor’s intended save and preview controls and test a reversed transition. If a button is configured to change Stage before running, make that consequence clear in its name.

Chapter 7 Landscape portrait and destination routing

Pulse Weaver’s native portrait canvas is a separate OBS canvas, documented at 1080 × 1920 in the earlier architecture. Each format needs its own layout, crop, browser viewport and source-item targets. A vertical version is not simply the landscape frame stretched tall. The latest wizard shows independent compositions and allows separate artwork and transitions.

A Stage can map scenes to destinations and exclude selected sources. The outputs that are actually enabled depend on the output plan and supported platform combination. Twitch dual format depends on Enhanced Broadcasting eligibility and negotiation. The project’s older documents disagree about Kick portrait capability; inspect the installed output selector instead of assuming it is supported.

When routing requires different exclusions or scenes, Pulse Weaver can use destination-specific rendering copies. Shared programme textures and canvases can reduce redundant work where routes align, but more outputs, browser sources and encoders consume resources. Twitch Dual is documented as sharing an audio exclusion mix across both formats in the relevant earlier implementation.

Recording may offer Default, Off, landscape, portrait and Both depending on build and settings. Routed recordings can have their own exclusions. Additional encoding and storage are real costs. The documented conservative multi-output 1080p60 baseline is Windows 10/11 64-bit, i5-12400F, RTX 3060, 32 GB RAM and 2 GB storage; it is the developer’s tested baseline, not a universal minimum for all shows.

Chapter 8 Show Control in practice

Show is the operator’s surface for the active show: Stage and output controls, landscape and portrait previews, chat, activity and a compact mixer. Control is the place to design or rehearse saved Looks in the current workflow. Camera is the more general scene/source editor. Layouts, labels and exposed controls vary by version.

During a live session, inspect the Stage name, the two formats and each destination’s status. Per-output statistics can include state, elapsed time, bitrate and dropped frames. A single overall indicator does not establish that every destination is healthy. Changing a Stage is separate from starting or stopping outputs.

Go Live preflight is intended to show and validate the selected output plan before the operator confirms. It cannot guarantee every service will succeed or remain healthy. If a whole-show start partially fails, inspect the actual destination states; some may have started while others did not.

The mixer exposes key operational controls such as level and mute, while the full OBS-style mixer and filters provide deeper configuration. Mute and volume on a shared source can affect every place that source is used; destination-specific exclusions are a different operation.

Chapter 9 Audio overlays and source lifecycle

An overlay is usually a browser source or another visual layer inside a scene. Its visual visibility, browser lifecycle and audio are separate. A hidden browser may remain loaded so a timer or widget retains state; whether it continues, restarts or produces audio depends on its settings and its provider.

The 2.0 wizard offers up to three shared alert layers per format, with layer 3 above 2 and 1. New browser copies start silent; choose an intended audible copy and verify the resulting sound on each desired output. Avoid duplicate alert sounds, but do not assume muting every portrait copy is correct for every audio route.

An actual provider browser URL is distinct from a template import or download link. Import the template into its provider first, then use the browser link it supplies. A hosted Lumia or StreamElements overlay remains hosted by its provider; importing its URL does not convert the provider’s proprietary project into a native editable project.

The main 2.0 release notes say unfinished Alerts and Overlay Designer entry points are hidden. Earlier status files describe an overlay designer and unreleased alert work. Treat those as historic or development information rather than promising they are visible in the 2.0.1 regular interface. Lumia templates require Lumia Stream.

A countdown has three separable components: display, timer state and completion action. Two canvas displays can represent one timer, but choose one completion-command owner so the same end event is not fired twice. Starting the broadcast is a further distinct action. Test a short countdown with outputs stopped before attaching a live transition or command.

Chapter 10 Worked shows and run of show

A gameplay show

Create Gameplay and Presenter Focus as live Looks in Main. In landscape, Game leads can use the full canvas with a small camera inset. Presenter Focus can enlarge the camera while retaining the game as a smaller panel. In portrait, stack camera and game vertically with independent crop. Check that essential game HUD elements remain visible.

Start on a separate Starting Stage. After the opening, activate Main and run Gameplay. Between matches run Presenter Focus, answer chat, then return to Gameplay. Select Break when away. Select Ending for the close, then deliberately stop each intended output. Do not assume Ending stops the stream.

A maker or project show

Use Face + activity and Activity + face as related live layouts. Bind the presenter and a desk, printer or instrument camera. On landscape, let the activity dominate with a presenter inset. On portrait, put the presenter and activity in an intentional stack. Move between the Looks when demonstrating a detail and explaining it. Keep each camera’s frame and treatment aligned with its capture unit.

A camera-free show

Choose Gameplay or Screen share without an optional face camera, or choose only Starting, Break and Ending screens. This illustrates that an input is required only when the chosen layout needs it. Add a camera later if the content and setup call for it.

A coordinated closing sequence

A closing screen may include provider artwork, a credits widget and a thank-you message. Enter the appropriate Ending Stage or Look in your own show design, then verify the credits lifecycle and audio. A specific older BRB/Ending repair demonstrated full-canvas motion between Looks; its timings and Lumia credits bridge are not automatically installed defaults for every show.

Chapter 11 Chat platforms and audience activity

The unified feed can combine Twitch, YouTube and Kick chat, with platform identities and available role or badge data. Reading filters and send destinations are separate decisions. Moderation and sending require the appropriate account grants and are subject to each platform’s capabilities.

The 2.0.1 README says incoming YouTube messages use a web scanner; sending, moderation and broadcast management use the official API. Earlier releases used different receive mechanisms, including polling and an experimental streaming reader. A web format change, private or restricted chat, permissions, network availability and quota can affect operation. Web reception is not a claim of zero API use.

Discord support in 2.0 is receive-only. Pulse, the Discord bot, and the signed-in user both need access to selected channels. Up to five channels in one server can be read alongside the streaming chats. The composer sends to streaming platforms, not Discord. The All chats without Discord filter keeps stream messages visible while Discord remains connected.

Kick incoming events are described in the earlier status as using a hosted relay, so not every event path is purely local. Version and packaging affect application registrations: the 2.0.1 README describes packaged Twitch, Kick and YouTube registrations, with optional custom credentials. The older public-preview instructions requiring users to supply certain registrations are not a reliable guide to 2.0.1.

Chapter 12 Lumia and external controls

Lumia Stream is a separate application. Its PulseWeaver Stream Studio companion can operate existing Stages, saved Looks or motion actions, source visibility, audio, media and configured outputs, subject to the installed plugin version. Plugin 1.5.1 documents temporary Look undo, the configured show, individual destinations, recording and fifteen keypad alerts. Its operating surface does not create scenes or edit source transforms and filters.

The 2.0 on-screen keypad can trigger fifteen Lumia alerts. Give buttons meaningful names and icons and enable the relevant alerts in Lumia; plugin alerts default to Off. Plugin 1.5.1 retains the Motion Preview plugin identity and existing action bindings. The regular installation defaults to local port 18755, while isolated copies may use different saved ports.

The local API uses an authenticated loopback connection. Keep its bearer token private. The Streamer.bot example in the workspace describes curated Stage, scene-item, audio, recording and replay controls; it is a local example, not an assertion that arbitrary Streamer.bot actions or remote connections are supported by every release. An accepted recording request may still require checking the observed result.

OBS WebSocket can be used by compatible external tools and is included in OBS, but Pulse Weaver’s own integration does not depend on it. Plugin compatibility and exact API routes should be checked against the installed release. https://obsproject.com/kb/remote-control-guide

Chapter 13 HUD and the desktop

Pulse Weaver 2.0 includes one independent transparent desktop HUD. In Camera, choose HUD and select a display; its physical pixel dimensions determine the HUD canvas. Add and arrange sources there. The monitor control shows or hides the borderless click-through output over normal desktop windows.

The HUD is not a broadcast Stage or Look. Changing a Stage, Look or Camera tab does not itself change the HUD. It starts off when the application launches; the selected display is remembered. Disconnecting the display, changing scene collections or resetting the graphics device stops it.

The documented Windows implementation uses Direct3D 11 and SDR premultiplied-alpha desktop composition. Exclusive fullscreen and protected content require separate compatibility testing. Display Capture may capture the HUD, so check whether that is desirable for your show. The checkerboard is an editor aid and is not sent to the desktop output.

Chapter 14 Installation updates and privacy

The regular Windows installer is separate from ordinary OBS and preserves the Pulse Weaver configuration during a normal update. The project documents verified application-and-settings backups and a restore path. Backups can contain account data. External media files referenced by scenes are not necessarily included, so maintain separate backups of those assets.

Stop outputs and close Pulse Weaver before installing a replacement. Regular, alpha, unstable, isolated preview, Lite and Mac editions are not interchangeable simply because their version numbers look similar. Check the installation identity, target and channel before updating or restoring. Automatic update checks do not imply automatic installation in the documented updater.

OBS setup import copies supported profiles and scene collections into Pulse Weaver under collision-safe names. It does not install missing plugin binaries or copy every external file. Check devices, source types, paths, filters, credentials and format-specific layouts after import.

The 2.0.1 README says saved OAuth credentials are protected with Windows DPAPI for the current Windows account, and YouTube custom app credentials are optional. Disconnect before changing the app registration and save an ID and secret together. The configuration folder and local API token can contain sensitive access information and should not be shared in public exports.

Chapter 15 Under the hood and customization

The native engine and UI run together and call libobs and the OBS frontend API. The codebase also contains older WPF reference material; the architecture identifies the native application as the product runtime. Sources, scenes, canvases, video and audio mixes, encoders and outputs remain OBS-derived concepts.

The custom-show guide describes three related stores in the checked build: the OBS scene collection contains sources and scene items; pulseweaver-stages.json stores Stage assignments and transitions; pulseweaver-motion-actions.json stores named motion actions and targets. Treat this as version-specific implementation detail, not a stable invitation to edit files while the application is running.

For custom work, first identify the actual installation, active profile and collection, canvas dimensions, source identities and output assignments. Back up related state together. Preserve unknown fields and existing identities, stop outputs, and use a closed-app or isolated workflow when changing files directly. A scene named Vert is not proof it belongs to the native portrait canvas.

The guide warns that OBS scene data can contain relative as well as absolute coordinates. An edit to only one representation can load incorrectly. The native editor and APIs are safer for ordinary changes; complex migration should use the matching version’s implementation and verify after reload. The documented API does not imply an arbitrary custom-show authoring endpoint.

Pulse AI appears in older architecture notes as a constrained Codex CLI operation boundary. The newer README also describes using a user’s own Codex with a custom-show guide. These are distinct workflows and their presence should not be assumed from the existence of documentation alone. The supplied custom-show guide itself is reference material, not authorization to modify an installation.

Chapter 16 Troubleshooting and rehearsal

Nothing moves: confirm you ran the Look rather than merely selected it for editing; check Stage policy, item identities, saved targets and the relevant canvas.

Portrait is wrong: verify portrait scene ownership, artwork viewport, crop and the portrait target independently of landscape.

A border stays behind: the capture, mask and frame may be separate items; inspect whether they are controlled as one visual unit.

An old overlay remains: check explicit hidden targets, nested scenes, layer order and destination-specific routing.

A countdown appears but does not run: its display and timer-start command are separate. Check the provider and designated event owner.

The countdown fires twice: check for two canvas copies or automations both owning the completion command.

A Stage changes but the stream stays off: that is expected unless a separate output action starts it.

One platform is wrong: inspect its route, exclusions, output status and actual platform preview rather than relying only on the main canvas.

An edit appears live: the item or shared source may belong to the active programme; editor selection alone does not make all changes private.

A strong rehearsal checks both directions of each Look change, multiple points along the movement, both canvases, layer order, audio, source lifecycle and each destination. Confirm that repeated triggers do not duplicate chat, audio, timer completion or other external actions. Keep a recovery copy of the relevant configuration and separately referenced media.

Chapter 17 Release evolution

The early 1.8 and 1.9 records document an earlier product and native transition. The 1.11 line developed destination-aware Stage operation, dual formats, cross-platform chat, audio routing, output monitoring and interface themes. The 1.12 line concentrated on portrait editor parity, routing and audio exclusions, credentials, updater recovery and runtime reliability.

The 1.13 alpha line introduced saved Stage Looks and source animation, followed by builder, platform and chat work. The 1.14 line expanded the Control experience, guided setup, chat providers, motion refinements and Lumia integrations. Earlier setup guides describing four pages are historical for the default 2.0 builder.

The 2.0 unstable line developed selection-first setup, smoother motion, receive-only Discord and a separate desktop HUD. The 2.0.0 regular notes promoted these features. The local 2.0.1 notes describe Manage Stages layout improvements and companion help updates. The appendix preserves the available individual release notes rather than treating historical entries as current guarantees.

The public release feed establishes the published records available on 4 November 2026. Local private betas, engineering handoffs and unpublished builds are a separate history; the final appendix preserves the local installer notices and status record with their non-public or uncertain status clearly labelled.

Scene

Appendix D Practical tricks and operator checklists

Before adding another Look

Name the presentation by the choice you will make live: Game leads, Presenter reacts, Workbench detail.

Reuse the same intended scene item within a canvas when you want it to move continuously. Landscape and portrait still have separate item identities and geometry.

Treat color, logo, crop and border as setup options unless you plan to choose between them on air.

Give items that should disappear an explicit hidden or off-canvas target in each Look. Otherwise an earlier layer may remain visible.

Keep the original show and create an additional show or saved layout when experimenting; confirm what Finish will add before committing.

Quick framing and layering checks

Fit versus crop: fitting preserves the whole source and may leave empty space; cropping fills the target but can cut off faces, game HUDs or text. Check both the source and its destination canvas.

A browser page viewport and its scene-item transform are separate settings. Set the browser dimensions for the intended canvas, then verify the item bounds and scale.

Layer order is bottom to top. Keep full-screen opaque artwork below cameras and alerts that must remain visible. Check the topmost alert layer after changing Looks.

Do not stretch a camera simply to fill portrait. Adjust the crop and framing on the portrait canvas.

Confirm overlay URLs are the provider’s browser links, not marketplace, share, import or download pages.

Quick audio and overlay checks

A source-level mute or volume change may affect that source in every scene where it is used. A destination exclusion is a different control.

Check which browser copy supplies alert sound. The wizard’s new alert copies start silent; enable the intended copy and test each route.

Avoid making both portrait and landscape timer copies run the same completion command. Choose one completion owner and one intended sound owner.

A hidden browser source may remain loaded. Verify whether a timer should continue, an animation should restart or a widget should replay when shown.

Check recording tracks and monitoring separately from visual visibility; an audio source can be heard without appearing as a visible scene item.

Preflight and rehearsal checklist

Confirm the active show, Stage, and selected Look before a time-critical cue.

Read the output plan and verify each destination’s format, connection and status. A Stage change does not start the stream.

Inspect landscape and portrait previews independently. Confirm crops, artwork, chat and alert placement.

For a new movement, inspect the beginning, middle, end and return path. Check background coverage and attached frames.

Test audio and any timer or Lumia command with outputs stopped or in a disposable profile first.

After a partial output failure, inspect each destination separately; do not infer that all outputs succeeded or stopped together.

Keep the configuration backup and referenced artwork/media together. The installation backup may not include external files.

After importing OBS scenes, confirm source types, device identities, media paths, filters, audio, plugin dependencies and canvas ownership.

Recovery and identity tips

When a Look stops working after a source rename, check stable identity and the actual saved target before recreating the camera. When a source is deleted and re-added, its new UUID is not the old identity even if the name is identical. When updating a show file offline, close the application first, back up the active collection and its Stage/motion stores together, preserve unknown fields and validate after reload. Never treat a file with a plausible OBS name as the active profile until the installation and active collection have been identified.

For transition problems, separate four questions: did the Stage change; did the assigned scene change; did the Look apply; did the routed destination receive it? This narrows the fault to cue selection, saved target, renderer or route. For an overlay problem, separately check URL, browser dimensions, item bounds, visibility, layer order, audio and activation lifecycle.

Remaining preview limitations

A real Twitch account/channel is still required to validate live delivery and streaming eligibility. The Google project, YouTube API, desktop OAuth client, sensitive YouTube scope and initial test user are configured, but the user must still approve the account consent flow inside Pulse Weaver before a real YouTube broadcast can be validated.

Twitch dual-format output depends on Twitch Enhanced Broadcasting eligibility and negotiation.

The custom vertical canvas does not yet expose a separate transition palette.

The overlay designer has visual positioning and numeric sizing/rotation, but not a full keyframe timeline, nested groups, masks, or snapping guides.

Hosted third-party overlays import by URL; Pulse Weaver does not reverse-engineer or convert proprietary Lumia/StreamElements project files.

Device discovery finds endpoints; provider pairing/discovery metadata still has to be completed in the provider's normal way (for example, obtaining a Hue username or Home Assistant token).

Kick incoming chat and events use Pulse Weaver's hosted relay. The relay validates Kick's RSA webhook signature and timestamp, deduplicates message IDs, isolates delivery by broadcaster, issues short-lived hashed desktop sessions, and retains queued events for only 15 minutes. Users do not enter a relay address or expose a port on their PC.

YouTube live chat, paid memberships, membership gifts, milestones, Super Chats and Super Stickers are polled through the signed-in account and published to alerts/automations. New public channel subscribers are polled as youtube.channel.subscribe and normalize to audience.followed; YouTube does not reveal private subscriber identities. Kick's event keys and cross-platform semantic aliases are delivered through the signed relay. Advanced lighting protocols such as MQTT, OSC, MIDI, and Art-Net remain extension work.

The older WPF code under src/ is migration/reference material only and is not shipped as the product runtime.
