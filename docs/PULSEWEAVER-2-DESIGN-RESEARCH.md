# Pulse Weaver 2.0 native preview: research and parity contract

Research date: 17 October 2026. Target revision: **2.0.0-unstable.2**. Initial source baseline inspected: `6a98d4a05dc9c04e70855cff8e2c9cf08388c6c1`, followed by the native preview and its revised shell. This is a design rationale and acceptance checklist, not evidence that a finished design has passed a user study. The preview remains a native Qt/OBS application. A visual redesign must preserve the current streaming, motion, audio and automation semantics.

## Research applied to this product

| Primary source | Principle supported by the source | Recommendation for Pulse Weaver |
|---|---|---|
| [University of Maryland: Shneiderman's Eight Golden Rules](https://www.cs.umd.edu/~ben/goldenrules.html) | Consistency, informative feedback, error prevention, reversible actions, operator control and less memory burden. The author explicitly says principles need domain-specific validation. | Keep one vocabulary for Stage, Look, programme, preview and destination. Show active state near its control. Disable unavailable edits; when a live edit is rejected, display the accepted selection. Keep previews and live controls visible during routine work. |
| [Stanford CS147: Visual Design, Terry Winograd](https://hci.stanford.edu/courses/cs147/2006/slides/07-visual/147-visual.pdf) | Grouping, alignment, negative space and visual hierarchy help organization; interference, excessive ornament and distracting motion damage it. | Group by task: monitor the programme, select a Stage/Look, route destinations, check audio, operate transport. Use a common grid and spacing. Reserve the strongest visual weight for active live/recording state and consequential controls. |
| [MIT DesignFTW: Animation and Feedback](https://designftw.mit.edu/lectures/animation/) | Motion can explain relationships and outcomes; frequent animations should be brief and avoid distraction. Accessibility needs consideration. | Keep the approved sliding selection thumb, triggered by a user action and stopped after settling. Avoid perpetual decorative motion. Honor the interaction-feedback preference and make focus/selection legible when animation is disabled. |

These recommendations are an application of those principles, not a claim that a particular layout is scientifically optimal. Test whether an operator can find and complete real tasks without coaching. The user's explicit design preference takes priority over a generic interface pattern: **click through instead of long lists**. Present primary workflows as a small set of category cards, then a focused detail/action page with an obvious Back control. Retain advanced native menus as an escape hatch; do not make a new long menu or palette the main way to use the product.

Recommended hierarchy: four prominent, permanently visible workspace controls for **Show**, **Lights**, **Camera** and **Action**. Show contains operation and Control's stage/Look rehearsal; Action contains connections and basic automation. Settings/Studio remain subordinate utilities. Lights must mount its retained device/control implementation, with click-through device and saved-look cards; changing its label alone is not feature restoration. Platform color should supplement text and checked state. Keep unselected route choices neutral and recording's selected state yellow-orange as already approved.

For **Stage selection**, open a grid of named Stage cards with current selection, orientation/route summary and optional useful preview; keep `pulseStageSelector` as a hidden model adapter so existing callbacks, live guards and automation continue working. Selecting a card commits its stable Stage identity once. Do not replace the hidden adapter with a second independent source of truth.

For **Commands and setup**, first choose a category such as Show, Audio, Recording, Sources or Automation, then choose a small set of relevant action cards. Search may filter cards within that context, but the default experience must not be one long command list. Go live, Record and other consequential commands require a deliberate action; typing or submitting a search must not run the first match. Back/Esc returns to the previous category or show and restores focus without firing a command. This document's tables and checklists describe engineering coverage; they are not proposed product-screen lists.

### Revised geometry and visual acceptance

At a native 1180×720 window and 100% display scale, require all four main workspace controls to be fully visible and non-overlapping, at least 120×42 px, with resolved text at least 14 px/semibold and icons at least 22×22 px. Their ordinary state must look clickable, rather than disappearing into a transparent text rail. Utilities must not squeeze or replace the main workspace controls.

With audio collapsed, require both programme frames to begin at or above y=160 and retain at least 280 px of fully visible height; retain at least 280 px of chat width. This improves the first preview's y=239/212 px programme footprint. Health and transport stay fully visible. Preview toggle/rate changes and long status text must not move programme/chat rectangles. Expanded audio keeps health/stop controls visible and collapsing it restores the former geometry. Provider and recording tracks retain 32 px height, and recording retains its 150–240 px width constraint.

Use the approved slider's tactile language across workspace and action buttons: a restrained cap gradient, upper highlight, lower rim/shadow, visible pressed state and consistent corner/spacing tokens. Quiet card panels can remain visually flatter than actionable controls. Use a common themed role for icon utilities instead of scattered hard-coded QSS. Preserve explicit geometry-only exceptions where native containment tests justify them; the Commands category card's 66 px content plus border is one such case. Theme changes must not alter controller behavior or introduce idle animation.

Click-through cards must retain enough height for their painted title and detail: 94 px for Commands and 110 px for the six setup categories. Backend setup option cards retain their source-computed minimum, at least 64 px, without overlap. Check full ancestor containment in the resolved native theme. The passive native audit may open the show wizard's stage-group page and cancel, without creating a show. An inherited ordinary-button height can clip all card text even when the card count and scroll reachability checks pass.

## Main control parity checklist

Every row needs a reachable control, meaningful keyboard/focus behavior, accepted-state feedback and persistence where the old control persists. A moved control is not a removed capability.

| Area | Existing behavior to preserve | Presentation/acceptance condition |
|---|---|---|
| Navigation | Show/Control switch; working Lights mount; Camera; account/Action workspace; Settings; Plugins; native Studio menus. | Four large permanent workspace controls satisfy the geometry/typography criteria above. Secondary category cards lead to focused detail pages with visible Back and preserved state. Keep advanced native menus reachable without promoting a new long list as the primary interface. |
| Programme previews | Separate landscape and portrait programme views; provider/scene labels; preview cycling; missing-portrait repair. | Preserve useful preview and chat area. Neither diagnostic text nor toggling preview options changes their allocated rectangles. Preview is clearly distinguished from Control's rehearsal/editor. |
| Preview workload | Live previews while streaming; selected preview refresh rate. | Setting changes preview rendering only, not stream FPS or encoder settings. State is visible, persisted, and keyboard operable. |
| Output health | Provider/format selection, ready/starting/live/stopping/error, uptime, bitrate, dropped frames and details. | Show truthful actual output state; start request acceptance is not success. Long errors wrap or use details without moving core controls. |
| Stage operation | Stage selector; capture current; manage stages; build first show; per-landscape/per-portrait transition choice and saved stingers. | Stage cards form a grid picker backed by the existing hidden combo/model. Long names remain discoverable. Stage/Look vocabulary and orientation are explicit. Stingers and native Move continue working. |
| Capture shortcut | Choose Game Capture source, choose game window, refresh windows, specific-window mode and source settings. | Use a capture category/detail path with contextual choices rather than a new all-source list. Unavailable or vanished game/source is reported without silently selecting another window. |
| Provider routes | Twitch `off/horizontal/dual`; YouTube `off/horizontal/vertical/dual`; Kick `off/horizontal`. | Preserve exact backend values and capability restrictions. Live veto rolls the visible thumb back; one click commits once. Off means Off. |
| Recording format | `standard`, `off`, `horizontal`, `vertical`, `dual`. Standard is labeled **Default** and uses native recording settings; routed modes are separate MKV recording paths. | All five remain available. Do not merge Default into 16:9. Same segment size across providers/recording; the current recording slot is 150–240 px wide and 32 px high. Lock format while recording. |
| Transport | Replay buffer, virtual camera, Record/Stop and Go live/Stop all live outputs. Native recording pause/save replay remain reachable where supported. | Consequential active/starting state is visible and repeat clicks cannot duplicate starts. Keep stop controls reachable at small window sizes. |
| Audio | Compact meters, source faders, mute, monitor; collapse and full mixer. | Meters represent real sources; monitoring is not confused with output routing. Layout changes must not recreate/deactivate audio-bearing sources. |
| Chat | Native combined messages; read-provider filter; timestamps; send-provider choice, text and send; new-message navigation; provider moderation; custom browser panels. | Keep panel add/edit/remove/reload/browser/zoom and Lumia chat-only/full Control Room modes reachable through context/overflow. Respect unsupported moderation capability. Never send a message as part of a visual test. |
| Lights | Retained device setup, provider requests, power/brightness/color controls and local saved Looks. | Device/Look cards lead to selected details and Back; hidden models retain settings/callback authority. Loading a saved Look changes local controls, while sending it remains an explicit action. Native layout QA never clicks Test, Discover or Apply. |
| Automation | Existing Lumia/API controls and saved motion/action/source IDs. | Category and action cards provide click-through discovery; no long catch-all command palette. Navigation/labels do not alter protocol names or persistent UUIDs. Display connection/task progress without claiming unsupported integrations exist. |

## Secondary capability checklist

Keep these reachable through focused category/detail pages without overcrowding Show. Each page exposes only controls relevant to the selected task, with Back retaining context:

- **Control/Look editor:** Stage groups, Look creation/edit/rehearsal, source transforms/visibility, native Move timing/easing, transitions and stingers, actions, undo/rollback and shared-source reuse.
- **Stage manager:** Stage grid → selected Stage details → New/duplicate/delete, per-provider/per-canvas scenes, Leave unchanged, exclusions, per-orientation transitions and unavailable Kick portrait indication. A hidden combo may retain native/controller compatibility; it is not the public picker.
- **Camera/editor:** Landscape/portrait selection, scenes/sources, source properties/filters, transforms, native docks, unlock/reset layout, overlay designer, import OBS profiles/collections and optional service data.
- **Connections:** Twitch/YouTube/Kick authorization/disconnection and account status; supported title/category/privacy/description details; only enabled routes start; provider-specific errors remain visible.
- **Lights:** Device cards, selected-device control page, saved-look cards and explicit device setup; retained provider/settings callbacks. Hardware compatibility and bridge trust are verified separately from showing the controls.
- **Settings:** Category cards → focused settings: guided Build my show; destination bitrates; capture devices; canvas/output resolution and FPS; recording folder/container; desktop/microphone devices; six track names and memberships; monitoring device/mode; Twitch VOD track; API port; themes/feedback; update/recovery; advanced native OBS settings. Avoid a long public sidebar or giant combined form as the new default.
- **Native menus/plugins:** File, Edit, View, Docks, Profile, Scene Collection, Tools, Help, plugin docks, logs and legal/help entry points. Preserve existing Altron tools if included in this full preview; do not import Lite's intentional feature reductions.
- **Source/audio lifetime:** Shared source UUIDs, nested scene/group references, global audio, browser alert monitor mode and track masks must survive workspace changes. A redesign does not justify rebuilding the source graph.
- **Private state:** Account credentials and local API secrets remain in the isolated profile; nothing private enters source archives, runtime payloads, screenshots or validation output.

## Official SDK context and implementation boundaries

[OBS's frontend API](https://docs.obsproject.com/reference-frontend-api) provides separate starting/started/stopping/stopped events for streaming and recording, plus scene, transition, replay and virtual-camera events. Drive display state from existing application events/controllers. Reuse native actions and the current output coordinator rather than starting outputs from a new paint/widget layer. Check every API against the bundled headers: current online documentation may describe a newer OBS version. Scene/source handles have ownership rules; widgets must not keep unowned pointers beyond their lifetime.

[Twitch EventSub WebSocket handling](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/) distinguishes connection health, notifications, reconnect and revocation. An ordinary lost connection requires resubscription and missed events are not replayed. The [WebSocket reference](https://dev.twitch.tv/docs/eventsub/websocket-reference/) documents repeated delivery with the same message ID. Therefore connection state, account authorization and subscription readiness should be distinct; deduplicate by message ID and avoid a second subscription/alert path merely to populate a new panel. These are integration requirements, not evidence of an existing Pulse Weaver defect.

[Streamer.bot's official WebSocket requests](https://docs.streamer.bot/api/websocket/requests) use request IDs to correlate responses, require explicit subscription for raw-socket events, expose action IDs via GetActions, and execute actions through DoAction. A future WebSocket connector should discover capabilities and use stable action IDs rather than matching display labels. Its [authentication guide](https://docs.streamer.bot/api/websocket/guide/authentication) is the protocol authority. Do not present a connected/authorized state until the actual handshake succeeds. This preview instead provides a C# HTTP example that calls Pulse Weaver's own `/api/v1/control`; it is not a client for Streamer.bot's WebSocket server or an import-tested Streamer.bot bundle. Preserve existing Lumia compatibility independently.

For lighting, validate provider requests separately from UI navigation: [WLED's JSON API](https://kno.wled.ge/interfaces/json-api/) uses POST state updates with its own brightness/segment fields; [Home Assistant's REST API](https://contributors.home-assistant.io/core/internals/rest-api/) calls light actions with bearer authorization and action-specific data; [Hue's public getting-started guide](https://developers.meethue.com/develop/get-started-2/) changes legacy light state with HTTPS PUT. [Hue's published HTTPS requirement](https://developers.meethue.com/) does not establish that this preview has completed bridge certificate provisioning or hardware validation. Keep normal certificate checks; report failures honestly instead of silently trusting a bridge. These are request-format requirements, not a claim that physical devices were exercised.

## Focused validation strategy

1. **Controller contract:** Run `tests/StudioControls` against production controls. Cover every route/record value, one commit per click, repeated selection no-op, external backend updates, disabled changes, rejected live changes, all five recording modes, finite animation and idle paint count. Preserve existing larger-font and segment-size checks.
2. **Real native geometry:** Use the inert portable fixture and `PulseUiLayoutAudit.hpp`; capture 1280×1000 and 1180×720. Assert the revised navigation/density criteria, compare preview/chat/transport rectangles before/after preview toggle, rate changes and long diagnostics, and capture Show, Control, Camera, Action, Settings and Lights for shared-style review. Control's two Stage/Look strips remain 44 px high and their available native choice buttons remain fully contained at 36 px high; browsing Control must return to Show without saving or running a Look. Inspect full ancestor containment, not merely nonzero visible card area. Add actual 100/125/150/200% scaling review, tab order, visible focus, keyboard-only routes and recording; inspect screenshots for clipping, overlap and weak contrast. An equal JSON rectangle does not prove readable text.
3. **Task walkthrough:** Without live credentials or outputs: open a category, drill into a task, go Back; choose a Stage from its grid; find both transitions; select a game; alter each provider format; select Default recording; locate audio monitor/VOD exclusions; add/switch a chat panel; enter and leave Control and Camera; find logs and recovery. Browse Lights using only seeded TEST-NET device cards and a synthetic local Look; confirm credentials remain masked and no hardware action fires. Check card/grid keyboard movement, selected-state synchronization and focus restoration. Search/Enter/Back/Esc must not accidentally run an output command. Verify no settings silently reset and no primary workflow falls back to a long public list.
4. **Affected functional tests:** Use `OutputActivity`, `DestinationRouting`, `RuntimeSafety`, `MotionAudit`, `CameraEditor`, `StageExclusions`, `StageTransitionReentry`, `AudioSourceLifetime`, `ChatProviders` and `ChatRenderer` according to changed wiring. Existing stinger/cache work is validated separately; do not add repeated heavy media decoding to a layout-only check.
5. **Runtime budget:** Compare the same inert configuration before/after. Added timers, browser instances or offscreen redraw loops require justification. Keep native meters/display cadence; disable animations after settling. A static screenshot proves neither CPU nor RAM behavior.
6. **Packaging isolation:** Test exact preview installer identity, empty-profile first run, update/recovery, profile-copy adoption, and uninstall in a disposable target. Hash regular Alpha's executable, update identity and private configuration before/after; require unchanged. No real broadcast, chat send, live alert or regular-profile rewrite is needed for this audit.

## Isolated 2.0 preview packaging

At the inspected baseline, `packaging/Build-ChannelRelease.ps1 -Channel unstable` alone is **not isolated**: `PrivateSetup/Program.cs` gives regular/alpha/unstable the same `Pulse Weaver` installation directory, shortcut and `PulseWeaver` uninstall key. Motion Preview has a separate compile-time identity, but reusing that identity could replace a user's existing Motion Preview.

Use an explicit showcase/2.0 setup identity: **Pulse Weaver 2 Preview**, its own install directory, shortcut, uninstall/recovery filename and registry key. Keep regular Alpha's metadata and directories unchanged. A normal native portable build can be used: `OBSApp.cpp` resolves `BASE_PATH/config`; credentials and update preferences resolve from `applicationDir/../../config`. The separate installation root therefore isolates these files without changing the native motion-preview build flag. Recovery backup/work namespaces already derive from the install root.

`ProfileAdoption.cs` copies config into the destination while retaining its executable/update identity. Adoption is an explicit separate copy, never editing the source show. It also copies local API/OBS WebSocket ports and credentials: concurrent instances require deliberate distinct ports and an explicit client connection. Preserve existing Lumia protocol IDs; explain which instance the client controls. Do not distribute any adopted user profile.

The packaged `studio2-preview` identity gives a **fresh** native profile local API port **18775**; a valid explicitly saved port takes precedence. The Streamer.bot example and integration README use the same fresh default. This does not change regular's 18755 or Motion Preview's 18765. The historical 1.14.2 Builder Test also used 18775, so a port availability check is still required before concurrent use; a default is not a reservation. OBS WebSocket has its own port and must be considered separately.

Updater isolation needs an explicit proof, beyond the setup folder. The 2.0 implementation now establishes this contract:

- Schema-1 identity adds `product: "studio2-preview"` only for the isolated preview. `PulseUpdateRelease.hpp` constrains that product to `windows-unstable` and the exact `PulseWeaver-2-Preview-Setup-<version>-unstable.<revision>.exe` asset family. It rejects generic regular/alpha/stable fallbacks. Absent product markers retain regular behavior and cannot select the dedicated preview asset; malformed/unknown markers are rejected.
- `PulseGitHubUpdater.hpp` hides cross-channel opt-ins for this product and resolves `../../Uninstall Pulse Weaver 2 Preview.exe`. Regular recovery filenames and selection behavior remain unchanged.
- A downloaded installer is launched without a target-root override. Confirm the verified asset was compiled for the isolated product; a valid checksum of the wrong product is insufficient.
- Verify setup language/layout/test commands against the final compiled identity and exact payload, and verify profile adoption, rollback and uninstall leave regular Alpha untouched.

Focused `tests/Updates` metadata checks cover the product-family boundary, exact asset identity/digest, malformed/missing markers, paired asset families and the pre-existing regular-channel contracts. The packaging owner must still validate the final compiled setup switch/identity, payload and recovery behavior before calling the installer isolated.
